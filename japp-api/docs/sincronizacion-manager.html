Sincronización de ventas con el Manager

Cómo llega la venta de cada tienda al Manager central casi en tiempo real sin depender de internet para vender: cada cambio de una orden deja un aviso en una cola dentro de la misma transacción, y un agente manda la foto actual de la orden en cuanto puede. Reenviar nunca duplica nada.

Construido · en servicio
≈ 2 sun cambio llega al Manager con internet (LISTEN + 2 s para juntar)
60 sred de seguridad: ciclo y latido aunque no haya avisos
0duplicados: misma cola + Idempotency-Key + versión de la orden
∞ offlinela tienda sigue vendiendo; la cola espera y se pone al día

1 · Arquitectura

El agente es un proceso aparte en el servidor de la tienda (otro contenedor del mismo docker compose). Siempre llama la tienda al Manager; el Manager nunca entra en la tienda, así no hay que abrir puertos en el router del local.

3 · El ciclo del agente

  1. Un solo agente a la vez: pg_try_advisory_lock en una conexión dedicada. Si otro proceso lo tiene, este no envía.
  2. Se despierta con LISTEN sync_outbox (la API hace NOTIFY al encolar; «Enviar ahora» = POST /api/v2/sync/now), espera SYNC_DEBOUNCE_MS (2 s) para juntar lo que llegue a la vez y, como red de seguridad, cada SYNC_INTERVAL_SECONDS (60).
  3. Lote: hasta SYNC_BATCH (100) órdenes con avisos pendientes; de cada una, del primer al último aviso, se manda la foto actual. Cuerpo {agent: {version, sentAt}, transactions: [ … ]}, en gzip (SYNC_GZIP).
  4. Clave: Idempotency-Key: tx-{storeId}-{primer aviso}-{último aviso}. Un reintento manda los mismos bytes con la misma clave.
  5. Respuesta por transacción: accepted, duplicate o stale → enviada; conflict → aparcada; rejected → un intento más (aparcada al llegar a SYNC_MAX_ATTEMPTS, 10).
  6. Errores HTTP: 401/403 para el envío hasta que un latido vuelva a dar 200 (storeKey rechazada); 409 por clave usada con otro cuerpo → clave nueva; 413/422 → se parte el lote; otro 4xx → un intento; red caída, 408, 429 y 5xx → espera creciente de SYNC_RETRY_BASE_MS (5 s) a SYNC_RETRY_MAX_MS (60 s) y se repite.
  7. ¿Queda cola? Si el lote venía lleno (atraso por estar sin internet), repite enseguida hasta vaciarla.

4 · Cómo se evita la duplicidad

Capa 1 · tiendaOrden y aviso, mismo COMMITNo hay cambio sin aviso ni aviso sin cambio. Varios avisos de la misma orden se envían como una sola foto.
Capa 2 · transporteIdempotency-Key por loteSi se repite un lote con la misma clave, el Manager devuelve la respuesta guardada sin volver a procesar.
Capa 3 · ManagerVersión de la ordenCada transacción se guarda por orderId: una version igual es duplicate, una más vieja stale y nunca pisa a la nueva. Las facturas, únicas por storeId + serie + número.

5 · La transacción del día (una por cuenta)

GET /api/v2/transactions/day (y lo que llega al Manager con POST /api/v2/sync/transactions): una entrada por cuenta del día de negocio (apertura del periodo, hora de Madrid), con kind = invoice (cobrada y facturada), credit (abono), open (aún abierta) o cancelled. Todo actor es {user, role, device, at}.
